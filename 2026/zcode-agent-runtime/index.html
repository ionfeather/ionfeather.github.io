从 20 行 Agent 循环说起

任何一个学过 LLM API 的人，都能在一小时内编写出一个可以运行的 Agent。其核心只是一个循环：

while True:
    reply = model.chat(history)          # 把对话历史发给模型
    if reply.has_tool_calls:             # 模型想调工具？
        results = run_tools(reply.tool_calls)
        history.append(reply, results)   # 结果追加进历史，继续循环
    else:
        return reply.text                # 模型给出回答，结束

这段代码没有错误，在演示场景中也能正常工作。问题在于，它隐含了一系列假设，而这些假设只有在真实使用中才会失效：

朴素循环的假设真实世界
对话永远装得进上下文窗口长对话必然溢出
模型生成的工具参数总是合法模型的幻觉可能产生编造的、不合法的参数
用户会耐心等待 Agent 完成用户会中途插话、要求取消
每次模型调用都会成功流会中断、输出会截断、服务会繁忙
进程永远不会退出进程会崩溃，用户会关闭电脑
工具返回的结果都不大一次 grep 可能返回数百 KB

本文的主线即这张表：ZCode 运行时的几乎每个模块，都对应着某一条假设失效之后所建立的工程机制。 理解这些机制比理解循环本身更为重要——循环的写法人尽皆知，而这些机制才是演示程序与产品之间的分水岭。

研读方法：大型代码库无法通读。本文的做法是每次只抓住一条线索并走完全程。阅读源码时如果迷失方向，就回到一个问题上来：这段代码，是在保护上面那个循环的哪一步？

启动日志：运行时拓扑

思考：为什么桌面版要把 Agent 引擎打包成本地进程，而不是让界面调用云端服务？

最直接的原因藏在工具里：Coding Agent 的绝大多数工具（读写文件、执行命令、检索代码）操作的都是用户本机的文件系统，引擎必须在本机或能够直接访问工作区的环境中运行。由此形成的边界是：文件读取、命令执行和会话存储可以留在本地；模型调用是否依赖网络、选入上下文的代码是否发送给模型提供方，则取决于所选模型及其部署方式。

工具：连接 Agent 与环境

朴素循环中有一行 run_tools(reply.tool_calls)。围绕这一行可以提出三个问题：模型如何知道有哪些工具可以调用？参数传错了怎么办？工具返回数百 KB 的结果怎么办？这三个问题的答案，构成了 ZCode 工具系统的基本单元。

工具定义：三个组成部分

以 Glob（按文件名模式搜索文件）为例，它的全部定义只有一个 164 行的文件：

apps/zcode-cli/packages/core/src/tool/handlers/glob.ts

文件分为三段：handler（执行）、entry（自述档案）、formatModelContent（结果转译）。

// 第一段：handler，真正执行的函数
const globHandler: ToolHandler = async (input, context) => {
  const { pattern, path } = GlobInputSchema.parse(input);  // ① 运行时校验
  // ② 通过注入的端口搜索文件，而不是直接调用 fs
  const result = await context.fileSystemPort.searchFiles(
    { path: searchPath, pattern, maxResults: 100 },
    { signal: context.abortSignal },                        // ③ 取消信号一路传递到底
  );
  return { numFiles, filenames, truncated } satisfies GlobOutput;
};

// 第二段：ToolEntry，工具向系统声明的"档案"
export const globToolEntry: ToolEntry = {
  metadata: {
    name: "Glob",
    readOnly: true,          // 只读
    destructive: false,      // 无破坏性
    concurrentSafe: true,    // 可与其他工具并行
    timeoutMs: 30000,
  },
  inputSchema: GlobInputJsonSchema,     // 提供给模型的
  runtimeInputSchema: GlobInputSchema,  // 供运行时校验的
  permission: { needsApproval: false },
  resultBudget: { maxModelBytes: 100_000, strategy: "artifact" },
  handler: globHandler,
};

工具设计：三个问题

（1）同一份参数，为什么需要两套 schema？

inputSchema 是 JSON Schema，随 system prompt 发送给模型，是对模型的承诺：“调用我时请传这些参数”。runtimeInputSchema 是 Zod schema，在模型真正发起调用之后对参数进行校验，是对模型的防御。

为什么需要防御？因为模型的输出不可信：它可能把 path 写成数字，可能遗漏必填项，甚至可能幻觉出不存在的参数。如果不加校验直接执行，错误将在深层代码中以难以定位的方式暴露。在边界处校验，错误被拦截在原地，并且清晰的报错可以反馈给模型，使其有机会自我修正。

（2）handler 中为什么没有权限检查？

通读 globHandler 可以发现，它只负责搜索，不包含任何"这个操作是否安全"的判断。因为安全性并非通过代码检查，而是通过声明来表达的：

声明消费它的系统产生的行为
readOnly: true权限系统无需弹窗询问用户，直接执行
concurrentSafe: true工具调度器可与其他只读工具并行执行
timeoutMs: 30000执行器30 秒强制超时
resultBudget结果处理器超过 100KB 则写入磁盘保存为 artifact，仅向模型提供头部预览

可以对比另一种写法：在每个 handler 中手写 if (!hasPermission()) ...。这种做法的问题在于，策略分散在数十个工具之中，修改一次权限规则就需要改动数十处，并且难免有所遗漏。声明式设计将"事实"与"策略"分离：工具作者只负责如实描述"我是谁"，由系统统一决定"你能做什么"。

（3）为什么搜索文件需要经过 fileSystemPort？

handler 不直接调用 Node 的 fs 模块，而是调用 context.fileSystemPort——一个由外部注入的接口（Port）。本地运行时它是真实文件系统；远程 workspace 场景下它被替换为基于网络的实现；单元测试中则替换为内存中的假实现。

这体现了依赖注入在 Agent 工程中的标准用法，也是"core 不依赖具体环境"的落地方式：core 只依赖抽象，环境差异由装配层注入。

Q：如果要给 Glob 增加一条规则"禁止搜索 .git 目录"，应当修改哪里？

A：不是 handler——handler 不应承载策略，否则又会退化为分散各处的条件判断；也不能只在工具描述中写一句"请不要搜索 .git"——模型对描述的遵守是不可靠的，提示词无法真正约束行为。正确的位置是路径解析层（tool/path-policy.ts）：所有工具的路径都要经过它进行归一化与校验，在那里拦截只需一处改动，且对所有工具生效。

Turn：一次对话如何推进

用户输入一句"帮我重构这个函数"，到 Agent 给出回答，中间经历的全部过程称为一个 Turn。朴素循环中没有这个概念，但它是运行时调度的基本单位——取消、持久化、统计，全都建立在 Turn 之上。

其中第 1 步关系到单次执行的一致性。Turn 开始时，运行时会冻结模型与输出配置。之后即使用户切换模型，本次 Turn 仍沿用原有快照；否则同一个 Turn 的前后步骤可能使用不同模型，其定价、上下文窗口和能力边界都无法保持一致。

这体现了并发编程中的一个通用原则：配置可以变化，但单次执行必须基于一个一致的快照。 数据库事务的 MVCC、React 单次渲染中读取到固定的 props，都是同一思想的不同形态。

状态所有权：谁负责修改

阅读运行时代码最大的障碍是"状态究竟在哪里"。ZCode 对此的答案十分整齐：

状态所有者生命周期
全部运行时状态AgentRuntimeInternal（runtime/internal.ts:60）随会话
待执行的工作RuntimeCommandQueue（runtime/command-queue.ts:117）随会话
对话历史（内存）MessageHistoryImpl（agent/message-history.ts:135）随会话
对话历史（磁盘）SQLite session store（adapters/.../sqlite-session-store.ts）永久
单个 Turn 的状态ActiveTurnSteeringState随 Turn，结束即销毁

这一原则可以概括为：每块可变状态有且只有一个所有者，其他组件只能通过方法调用间接修改。 这一纪律使得任何 bug 的排查都有了明确的起点——状态不正确，就检查它的所有者。

主循环：模型请求如何推进

现在打开主循环本体 runRegularTurnLoop()（runtime/methods/turn-loop.ts:43）。出乎意料的是，它的骨架与开头的伪代码几乎一致：

while (true) {
  throwIfTurnAborted(state.turnAbortSignal);        // 每一轮先检查：用户取消了吗？
  // ……准备并执行一次模型请求……
  const result = await runModelBackedTurnStep(state, { ... });
  if (result === "break") break;                    // 由"这一步"决定循环是否继续
}

这里要先分清两个角色。循环负责"一轮接一轮地转"，但每一轮具体做什么、做完之后该不该停，由 runModelBackedTurnStep（一次模型步骤）决定。它返回三种结果之一："continue"（继续下一轮）、"output_continuation"（输出被截断，需要续写一轮）、"break"（结束）。循环只服从，不决策。

可以类比接力赛：裁判（循环）只看旗语决定要不要发下一棒，至于这一棒怎么跑、跑完是否完赛，由选手（每一步）自己判断。

下面的内容以五个递进的疑问展开，每个疑问都对应朴素循环没有回答、而真实代码必须处理的一件事。

模型为什么"记得"任务清单

从一个具体场景说起。让 Agent 修改 5 个文件，它会先用 TodoWrite 工具建立一张任务清单，然后逐项执行。问题在于：模型本身是无状态的，它不像程序一样把变量存在内存里。那么第五轮请求时，它为什么还知道清单做到哪一项了？

答案不是模型记住了，而是运行时每一轮都把最新的任务清单重新写进请求（turn-loop.ts:138-156）。每一轮请求发出前，运行时读取任务列表的当前状态，生成一段提醒文本注入进去。同类机制还有当前的运行模式、输出风格等。

于是可以得到一个重要结论：模型看到的上下文 = 对话历史 + 每轮重建的系统状态投影。 每一轮请求都像新员工入职第一天，运行时负责把"当前进展"贴在工位上，模型照单执行即可。这也顺带回答了"信息到底存在哪"：任务清单的权威版本在 store 里，对话中出现的那份只是每轮生成的快照。

每一轮开始前的检查单

飞行员每次起飞前都要过一遍检查单，无论已经飞过多少次。主循环的每一轮迭代也有一段固定的"检查单"，按顺序执行：

  1. 检查取消信号——用户是否按下了停止；
  2. 收集中途到达的消息——后台子 Agent 完成、后台任务通知等，追加进本次请求；
  3. 压缩检查——微压缩与自动压缩（详见后文"上下文装不下"一节），确保上下文装得下；
  4. 裁剪工具表——按本轮 Turn 的类型决定哪些工具可见。

最后一项可以用定时任务说明：定时任务的执行轮会被隐藏所有"创建、修改任务"的工具（turn-loop.ts:221-237）。原因很简单：不能让一个定时任务反过来修改它自己的定义，否则任务可以在执行中自我复制，失去控制。工具并非全部可见，而是在每次请求的边界处动态裁剪的。

为什么"取消"不能随意打断

这是本节最重要的一个发现，需要从模型 API 的一条硬性规定说起：对话历史中，每一次工具调用（tool_use）都必须有配对的工具结果（tool_result）。对 API 而言，对话历史像一本一问一答的账本——有问无答的账本会被整本拒收，后续所有请求都会报错。

现在设想：模型已经决定调用三个工具（三个 tool_use 已记入历史），工具正在执行，用户此时按下取消。系统能不能直接中断？不能——那会在账本上留下三笔"有问无答"。正确的做法是换一种方式执行取消（turn-tools.ts:142-144）：为每个未完成的调用补写一条"已取消"的结果（ToolCancelled），把账本补平，然后才结束。

这种"任何路径都不能破坏的结构要求"称为不变式（invariant）。历史的配对完整就是一条不变式，它值得付出代价来维护，因为对话历史不只是给用户看的记录——它同时是下一轮请求的输入。

循环什么时候才真正结束

直觉的答案是"模型不再调用工具时"。实际情况更谨慎：模型给出纯文本回答后，系统还要依次询问两个"还有没有人要补充"（turn-stop.ts:157）：

  1. 用户中途的插话（guide）还有没有？ 有——插话作为一条新的用户消息进入历史，循环继续；
  2. Stop hook（插件的收尾钩子）是否要补充上下文？ 要——补充内容注入历史，循环继续；
  3. 两者都没有——返回 "break"，循环真正结束。

因此，“结束"不是被动到达的终点，而是一个需要确认的决策点。

Q：为什么循环自己不判断"该不该停”，而要把决定权交给每一步？

A：因为判断所需的信息只在步骤内部——这一轮有没有工具调用、输出是否被截断、有没有插话涌入，循环在外面无从知晓。把决策封装在步骤里，循环才得以保持朴素。这正是开头的 20 行伪代码与真实代码骨架一致的原因：复杂度没有被消灭，而是被安放在了正确的位置。

并发输入：排队、插话与取消

朴素循环最深层的假设是：循环运行期间，世界是静止的。真实用户并非如此。Agent 执行任务期间，用户可能做三件事：发送新消息、对正在执行的任务插话、要求取消。本章依次讨论这三种情形。精读源码还会发现，每种情形的背后都至少保留着一条真实的竞态修复记录。

命令队列：串行化输入

设想 Agent 正在执行第一轮，用户连续发送了两条消息。如果允许它们并发进入循环，对话历史将被交错写坏——两个 Turn 同时向历史中追加消息，模型所看到的上下文将变得混乱。

ZCode 的做法是将"已被系统接受的用户输入"抽象为 RuntimeCommand（runtime/command-queue.ts:109），排入队列并串行消费。队列中的命令不止用户消息一种：

命令类型来源
prompt正常的用户提交
task-notification后台任务（如后台子 Agent）完成，唤醒主会话
subagent-message子 Agent 的回复，作为用户消息注入
control-only-turn仅记录一次配置变更

所有命令由 drainRuntimeCommandQueue()（runtime-command-queue.ts:37）依次取出执行，同一时刻只有一个前台命令在运行。所谓"准入（admission）"，就是在入口处消除并发，使循环内部可以假设自己独占执行。

这是并发设计中最常用的手段之一：与其在循环内部到处加锁，不如在边界处统一排队。队列将"同时到达的多件事"转化为"依次处理的一件件事"，内部代码因此可以写得像单线程一样直白。操作系统的调度器、Redis 的单线程命令处理，都是同一思想。

精读这个队列消费函数，还能发现两个朴素实现不会有的细节。

（1）后台通知会被合并。 如果队列中连续积压了多条后台任务通知，它们会被合并成一个模型轮次统一处理（runtime-command-queue.ts:43 的注释说明了原因：避免每条通知都单独发起一次模型请求）。十条通知若逐条处理需要发起十次模型请求，合并后只需一次。

（2）“立即执行排队消息"需要租约（lease）。 界面支持把一条正在排队的消息提前执行。这个操作的步骤是：停止当前任务 → 把目标消息出队 → 启动它。看似简单的三步，源码注释却记录了一个真实竞态（runtime-command-queue.ts:83-84）：“停止当前任务"与"目标命令出队"之间存在空窗期——停止只是发出信号，真正停下要等执行方感知——在此期间，一条不相关的后台通知可能抢先出队，占据本属于被提升消息的执行位置。修复方法是引入租约：先登记"前台提升租约”，再在同一个同步步骤内完成"匹配命令出队"与"消费租约"两个动作，使任何第三者都没有插入的空隙。

竞态问题的修复往往不是加锁，而是把两个动作合并为一个不可分割的步骤——数据库中称之为原子性，这里是同一种思想。

  • queue（排队）：等当前 Turn 结束后作为新命令处理——即"等它做完再说"。

插话的入口：五项检查

steerTurn() 接受一条插话之前，需要依次通过五项检查（steering.ts:57-114），任何一项不通过都会带着结构化的原因码被拒绝：

  1. 输入不能为空；
  2. 输入不能超过大小上限；
  3. 当前必须有正在运行的 Turn；
  4. 调用方声明的目标 Turn 必须与实际运行的一致；
  5. 当前 Turn 必须允许插话。

最后一项说明，并非所有 Turn 都可以插话——例如执行压缩的 Turn 就声明自己不可打断。

这套检查的意义在于：拒绝也是协议的一部分。 调用方得到的不是异常，而是明确的拒绝原因，界面可以据此决定是提示用户，还是改为排队。

guide 的消费：三条规则

guide 在工具批次边界处由 drainPendingInput()（steering.ts:1140）消费，源码注释中写着三条不直观的规则：

  1. 只取最早的一条 guide，普通排队消息不会被顺带取出——注释写明了理由：不能让未来的排队消息"偷跑"进当前 Turn；
  2. 已被预约的输入不能取——如果某条输入已被"立即执行"操作预约，普通消费必须暂停，否则同一条输入可能被消费两次；
  3. 消费后必须切换 queryId——下一次模型请求必须归属于这条新插话，否则后续的工具调用会被错误地归属于上一条用户消息（steering.ts:1175-1176）。

第三条处理的是归因一致性：消息不仅要进入历史，还必须归属于正确的来源。

此外，排队中的输入在消费之前仍可管理：删除、编辑重发、调整顺序分别有独立的入口（removePendingInputById、editPendingInputById、reorderPendingInput）。

（1）取消意图需要校验目标。 调用方可以声明 expectedForegroundExecutionId，即"我要停止的是那一次执行"。如果当前正在运行的已不是它（例如旧执行刚好结束、新执行已经开始），取消请求将被拒绝，而不是误伤新任务。这是过期请求防护：在异步系统中，“迟到的操作"与"越权的操作"需要以同等的谨慎对待。

（2）内部抢占与用户取消必须区分。 源码注释（runtime-command-queue.ts:463-465）记录了一个真实问题：“立即执行排队消息"需要先停止当前任务，这种内部停止与用户手动按下 Stop，过去共享同一种 cancelled 状态——导致系统误以为用户取消了整个队列，把自动消费队列的授权也一并关闭了。修复方法是把调用意图固定在当前这次执行上，使迟到的完成事件无法再篡改队列授权。

这两个细节共同说明：取消不是一次信号的传递，而是状态机中一次需要精确归因的转移。

Q：为什么"立即执行排队消息"这种看似简单的操作会引出租约机制？

A：因为"停止当前任务"和"开始新任务"之间存在异步空窗：停止是发出信号，真正的停止要等执行方感知；而入队、出队、通知唤醒都是并发的参与者。只要两个动作之间存在任何异步等待，第三者就可能插入。租约的本质是把"意图"显式登记为状态——先声明"接下来这个位置属于谁”，再执行——使抢占者即使到达，也能发现自己无权行动。

上下文：压缩

模型的上下文窗口是有限的，而对话是单调增长的，因此长对话必然溢出——这不是概率问题，而是时间问题。这是 Agent 产品化的第一道关卡。

朴素的做法是"装不下就截掉最早的”。但对话历史不是普通的文本流：工具调用与工具结果是成对出现的，截断操作容易留下"有结果、无调用"的孤儿消息，多数模型 API 会直接报错；况且早期消息中往往包含关键的原始需求。

ZCode 的方案是压缩（compaction）：用模型将过长的历史总结为摘要，以摘要替换原文。下面依次回答五个问题：什么时候触发、怎么判断"装不下"、压缩时模型收到了什么、压缩之后历史变成什么样、压缩机制自身失灵了怎么办。

四条路径的分工如下：

  • 自动压缩是常态：每次请求前检查，防患于未然；
  • 反应式压缩是兜底：token 估算不可能完全准确（提供商真实的 tokenizer 是黑盒），总会有漏网之鱼，因此捕获溢出错误后压缩并重试；恢复成功时无需用户介入；
  • 微压缩是轻量路径：完整压缩需要调用模型生成摘要，既慢又有成本；先清理冗长的旧工具输出，往往已经足够。

设计要点：四条路径不是四个功能的堆砌，而是同一件事的四种触发时机。其中重要的工程决策是让它们汇聚到同一个执行函数——压缩逻辑只有一份，四条路径永远不会发生行为上的漂移。

压缩阈值：何时触发

第一个问题是：运行时如何知道当前的对话占了多少 token？本地并没有模型真实的 tokenizer。ZCode 的答案是一个两级估算（compact.ts:313 的 buildProviderUsageTokenOverride）：

  1. 优先使用真实值：模型每次响应都会报告本次请求实际消耗的 token 数（usage）。运行时找到最近一次 assistant 响应中的这个真实数字，作为基数；
  2. 真实值之后的新消息，用粗估补足：本地估算的规则相当朴素——字符数 ÷ 3（ESTIMATED_TOKEN_CHAR_DIVISOR，shared/src/usage-stats.ts:9）。这个近似看似粗糙，但源码注释记录了一次真实的修正：旧版估算只统计消息正文，漏掉了工具调用的入参，导致大型工具参数实际占用了大量上下文，在估算里却被计为 0（compact/manual.ts:105-106）。

也就是说，估算的策略是"能拿到真值就用真值，拿不到的部分用粗估兜底"。

第二个问题是：超过多少算"装不下"？阈值并非一个经验常数，而是由一条公式算出（compact/policy.ts:67-88）：

有效窗口 = 上下文窗口 − 输出预留
阈值     = 有效窗口 − 13,000（安全缓冲）

以默认的 200K 窗口为例：输出预留取 21,000（源码注释说明了原因——早期版本按模型的最大输出完整预留，导致过早压缩，后来统一收敛到 21K），于是阈值约为 200,000 − 21,000 − 13,000 ≈ 166,000 token，即窗口的 83% 左右。

为什么必须预留输出空间？因为提供商声明的上下文窗口是输入与输出共享的：如果输入占满整个窗口，模型连一个字都输出不了。压缩只能压缩输入侧，所以阈值的分母必须先扣掉输出。

摘要提示词：保留什么

为什么要如此强硬？因为这次调用是"唯一的一轮"：模型若习惯性地去调工具，回合就浪费了，压缩失败。

（2）先分析，再总结。 要求模型先把分析过程写进 <analysis> 标签——按时间顺序逐段梳理对话——然后才输出 <summary>。这与"先想后答"的提示工程实践一致：显式的中间步骤能显著降低遗漏。

  • 用户消息必须逐条保留。模型做摘要时天然倾向于详细保留自己生成的内容、淡化用户的原话；但用户的原话承载着意图与约束，恰恰是压缩中最不能丢失的信息，所以 prompt 用一整节强制要求；
  • 下一步必须引用原文。prompt 要求"下一步"直接引用最近对话的原文（verbatim），并明确警告不要节外生枝——这是为了防止任务漂移：压缩之后 Agent 换了个方向自行其是，是摘要机制最典型的失败模式。

（4）安全约束逐字保留。 用户说过的"不要碰某类文件"“禁止某类操作"等约束，必须在摘要中原样保留——压缩不能成为绕过用户约束的漏洞。

压缩结果：摘要与近期消息

压缩不是"摘要替换一切”，而是摘要 + 最近消息原样保留的两段式结构：

压缩前：  [系统提示] [消息1] [消息2] …… [消息97]        （约 166K tokens）
压缩后：  [系统提示] [摘要消息] [最近若干条消息原样保留]  （远小于阈值）

摘要消息本身也有精心的设计（buildCompactSummaryMessage，compact/prompt.ts:133）。它以这样一段话开头：

This session is being continued from a previous conversation that ran out of
context. The summary below covers the earlier portion of the conversation.

摘要末尾还附上了完整对话记录的磁盘路径，告诉模型：如果摘要里的细节不够用，可以去读完整的原始记录：

If you need specific details from before compaction (like exact code snippets,
error messages, or content you generated), read the full transcript at: ...

这意味着压缩并未真正"丢弃"信息，而是把信息降级了：摘要是随身的笔记，写入磁盘的完整轨迹是可以随时回查的档案。摘要保存的是"大概率还会用到"的内容，档案保管的是"万一需要"的内容。

压缩防护：熔断与失败

压缩机制自身也可能失灵，ZCode 为它设置了两道相互独立的防护措施。

其一，rapid-refill 熔断器（compact.ts:230、turn-model-step.ts:753）。设想如下恶性循环：压缩 → 工具输出又把上下文填满 → 再次压缩 → 再次被填满……每一轮压缩摘要都在消耗模型调用成本，而上下文始终装不下。熔断器检测到"压缩后上下文被快速重新填满"这一模式，即停止压缩，避免无效循环。

其二，连续失败熔断（compact/policy.ts:14）。压缩本身是一次模型调用，同样可能失败。连续失败达到 3 次，shouldAutoCompact 直接返回 circuit_breaker，不再尝试——与其反复失败空耗，不如把错误尽快暴露出来。

两道防护措施应对的是两种不同的失效模式：前者防"压缩成功了但没有用"，后者防"压缩本身一直失败"。

Q：为什么摘要 prompt 要求列出"全部用户消息"，而不是让模型自己判断哪些重要？

A：因为摘要是模型写的，而模型的注意力分配与压缩的目标并不一致。模型倾向于详细保留"技术含量高的内容"（代码、方案），而用户的短消息——“不对，我要的是另一种方案”——在模型眼中可能显得不重要，却恰恰是意图纠偏的唯一记录。这类信息一旦丢失，压缩后的 Agent 会沿着被用户否决过的方向继续走。用结构化的强制要求替代模型的自由裁量，是把"已知会丢的东西"写进 checklist 的防御式提示工程。

持久化：崩溃后如何恢复

会话不能只存在于内存之中：进程会崩溃，用户会关闭电脑。朴素的做法是每隔一段时间将内存状态快照存盘，但若在两次快照之间崩溃，中间的操作就全部丢失了。

一种经典的解法是事件溯源（Event Sourcing）：不存"当前状态"，而是存"发生的每一件事"，就像记账不只记余额、而是记下每一笔流水，余额永远可以从流水推导出来。ZCode 的持久化设计可以从这个直觉出发来理解，但精读源码后会发现一个更准确的事实：ZCode 采用的是分层设计——事件流负责进程内的顺序与一致性，规范化的数据库表负责崩溃后的恢复。 两者各司其职。下面分四个问题展开讨论。

事件流：统一进程内顺序

运行时发生的一切——用户输入、模型输出、工具调用、压缩边界——都会产生一个事件，并经过唯一入口 appendEvent()（runtime/methods/events.ts:81）。这个函数做四件事：

    C --> D["记录工具用量"]

第一步解决的是事件排序：事件序号只由事件存储分配。源码里保留着一条修正记录（events.ts:86-88）：过去实时推送的事件带着默认序号 0，而重放路径读到的是存储分配的真实序号——同一个会话存在两套顺序事实。修复方式是让所有消费者只见到已分配序号的事件。这正是"状态各有其主"原则在顺序问题上的体现：序号只能有一个分配者。

持久化范围：哪些事件需要保留

注意上面流程图的第二步是"选择性持久化"。事件存储本身是进程内的（contracts/src/events/in-memory-session-event-store.ts），只有三类事件会写入持久存储（persistDurableSessionEvent，events.ts:263）：checkpoint 的创建、rewind 的触发、用户输入的排队台账——它们都具有长期语义，是崩溃之后必须被保留的事实。

对话的主体内容走的是另一条更直接的路径：用户消息、助手消息、工具结果随着 Turn 的推进直接写入 SQLite（回忆前文"先写入存储、再发起请求"——assistant 占位消息在模型请求发出之前就已持久化）。SQLite 中的主要表如下（adapters/.../migrations.ts 的 0001 基线）：

表内容
session会话元数据：目录、标题、创建时间
message / part消息及其组成部分（文本、推理、工具调用），对话的主体
todo任务清单
session_input用户输入台账：排队与插话的生命周期
session_entry通用条目：checkpoint、rewind 记录等
model_usage / turn_usage / tool_usage用量统计

冷恢复：从消息表重建会话

进程重启后的冷恢复（runtime/methods/resume.ts）并不重放事件流——内存中的事件流早已随进程消失。恢复的数据来源是消息表：

  1. 从 SQLite 读出该会话的全部 message 与 part；
  2. hydrateMessageHistoryFromSession 将它们重建为内存中的对话历史（大体积工具结果按引用从 artifact 存储取回）；
  3. 恢复 shell 环境、已读文件状态、压缩时间线、最近一条 assistant 消息的锚点等。

既然崩溃恢复不依赖事件流，那么前文提到的 rebuildProjection()（message-persistence.ts:385）这个重放事件的函数又是做什么的？它的完整实现只有两行：

const events = await this.eventStore.getEvents(this.sessionId);
return this.eventReducer.reduce(events);

它服务的是进程存活期间的一致性：rewind、压缩、配置变更之后，用内存中的事件流重建一次会话投影，确保所有消费者看到一致的状态。两层分工由此明确：事件流保证进程存活期间的顺序与一致，消息表保证进程崩溃之后的恢复。

内存管理：淘汰瞬态事件

事件流常驻内存，长会话中它自己也会膨胀——源码注释直接写明了这一担忧：如果追加时全量拷贝且永不淘汰，内存会随 token 线性增长（in-memory-session-event-store.ts:31）。解决办法是按 Turn 窗口淘汰瞬态事件：流式 chunk 这类只在当轮有意义的事件，在 Turn 结束并被下一轮取代后从内存清除；而序号计数器只增不减（第 65 行注释），淘汰不会造成序号重复。

Q：为什么不把事件流全部持久化，做成"纯粹的"事件溯源？

A：可以从"崩溃后谁来读"这个角度分析。恢复路径需要的是按时间排列的消息列表；UI 查询、rewind、删除操作面对的也都是消息——规范化表天然支撑这些需求。而事件的职责是进程内的顺序与一致性，把流式 chunk 这类高频瞬态事件全部持久化只会放大写入开销，对恢复没有帮助。只有具备长期语义的事件才值得被持久保存。选择持久化什么，取决于谁会在崩溃之后来读它。

故障恢复：常见失败与对策

回到开头的 20 行循环。其中只有一步网络调用 model.chat(history)，但这一步在现实中可能以十几种方式失败。ZCode 对每种失败都设有一条对应的恢复路径：

失败恢复策略位置

输出 token 达到上限提交已生成的部分，以续写提示开启新的一步turn-output-token-continuation.ts

观察这张表可以发现一个共同点：运行时会优先在内部尝试恢复。 如果重试、压缩或重新准入成功，用户无需处理其中的失败；只有恢复手段耗尽后，错误才会上浮给用户。

这是演示程序与产品级运行时的最后一道分界：demo 处理顺利路径（happy path），产品处理失败矩阵。 填满这张表依靠的不是聪明才智，而是线上坏案例的积累——表中每一行的背后，很可能都对应过一次真实的用户反馈。

子 Agent：隔离探索过程

前文反复出现一个问题：主 Agent 的上下文是稀缺资源——“压缩"一章的全部机制都在为它服务。而一个长任务中最占上下文的，往往不是关键决策，而是探索过程的中间输出：读文件、搜索、试错。子 Agent（Sub-agent）正是为解决这一问题而设计的：把探索性工作隔离到独立的上下文中执行，只把结论带回主会话。 入口位于 core/src/subagent/runner.ts:131。

前后台：两种运行方式

子 Agent 有两种形态，由 launch() 在入口处分流（runner.ts:141）：

前台子 Agent后台子 Agent
父 Turn阻塞等待继续执行
Abort 信号继承父 Turn 的独立的
结果返回直接作为工具结果完成时以 task-notification 命令唤醒主会话
追踪无需额外机制注册进 RuntimeTaskRegistry

子 Agent 并非全能：它的可用工具由 profile 决定（例如 Explore 类型的子 Agent 只有只读工具）——与主循环一章"工具表按 Turn 类型裁剪"是同一思想的延伸。

前台与后台的区分并非一成不变：以前台启动的子 Agent，可以在运行过程中转入后台。实现方式是一场三方竞赛（runner.ts:309-316 的 Promise.race）：

转后台时最关键的一步是 detachParent()：把子任务的取消信号从父级断开。原因在于：前台子 Agent 的取消信号继承自父 Turn，父级一旦取消，子任务随之终止；而它转入后台之后，语义上已经独立，父级的取消不应再波及它。所有权转移必须显式完成，否则就会出现"用户在主会话按下取消，却终止了后台中毫不相干的任务"这样的互相干扰。

运行限制：看门狗与派生边界

子 Agent 也是 Agent，同样可能陷入死循环或长时间无响应。运行时为它安装了看门狗（watchdog，runner.ts:208）：超过不活跃时限（默认与模型流式空闲超时一致）即强制中止。

看门狗的覆盖边界从启动阶段开始（runner.ts:217-218）：看门狗与取消保护不能等"会话就绪"之后再安装，因为子任务的持久化与恢复可能在就绪之前就永久挂起。保护机制的覆盖范围必须包含启动阶段本身，否则最危险的窗口恰好没有保护。

此外还有一种"预防式"的限制：闲时任务（idle-time task）被禁止派生后台子 Agent（runner.ts:150-151），注释说明了原因——单次执行的模型授权与动态鉴权不能脱离父循环的生命周期进入后台。有些并发不是实现不了，而是不允许发生。

完成通知：为何需要排队

后台子 Agent 完成时，结果不是通过回调函数直接交给主循环，而是包装成一条 task-notification 命令，排入"用户不等人"一章介绍过的主会话命令队列。系统没有为此引入新的并发机制：子 Agent 的回调、后台任务的唤醒、用户的新消息，在系统眼中是同一类东西，都是排队等待准入的命令。新功能复用旧机制，是系统复杂度保持可控的关键。

Q：为什么完成通知要走命令队列，而不是让子任务直接回调主循环？

A：直接回调会把并发重新引入主循环——回调可能发生在主循环的任意一个异步等待点上，主循环内部的"单线程假设"随之失效。排入队列后，通知只会在主循环的回合边界被消费，处理时机是确定的。这与"用户不等人"一章的准入思想完全一致：并发在入口处即被消除，无论并发的来源是用户还是子 Agent。

总结：运行时的六条原则

ZCode 运行时的设计可以概括为六条：

  1. 核心是一个朴素的循环：模型 → 工具 → 模型。所有复杂度都是这个循环的保护层。
  2. 状态各有其主：会话级、Turn 级、队列级状态严格分离，每块可变状态只有一个所有者。
  3. 并发在边界处消除：命令队列串行化外部输入，steering 处理中途插入，内部代码按单线程假设书写。
  4. 行为依靠声明：工具的安全性、超时、结果预算都是元数据，策略由系统统一实施。
  5. 失败就地消化：每种已知的失败模式都设有一条不打扰用户的恢复路径。
  6. 事件与存储分层：进程内的事件流统一顺序与投影，磁盘上的规范化表承担崩溃恢复——每层只承担一种职责。
