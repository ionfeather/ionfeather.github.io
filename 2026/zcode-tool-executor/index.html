从一行 run_tools 说起

在最朴素的 Agent 循环中，工具执行通常只有一行：

reply = model.chat(history)
results = run_tools(reply.tool_calls)
history.append(results)

如果只看这三行，模型给出工具名和参数，程序找到对应函数并执行即可。然而，一旦工具能够修改文件、运行命令或访问网络，run_tools 就不再是普通的函数分发器。

设想用户提出如下任务：

把 server.ts 中写死的端口改为读取环境变量，然后运行测试。

模型可能一次返回两个调用：

Edit({
  file_path: "server.ts",
  old_string: "const port = 3000;",
  new_string: "const port = Number(process.env.PORT ?? 3000);"
})
Bash({ command: "pnpm test" })

如果运行时收到后立即执行，会出现一系列问题：

看似自然的做法实际问题
相信模型给出的工具名工具可能不存在，名称也可能为空
把参数直接交给函数参数可能是 JSON 字符串、缺少字段，或语义上无法执行
两个调用一起 Promise.all测试可能在文件修改完成前开始
权限弹窗展示模型原始参数真正执行的规范化参数可能已经不同
用户拒绝后直接抛异常对话历史会留下没有结果的 tool_use
把命令输出完整发回模型数百 KB 的日志会迅速占满上下文
用户取消后立即退出同一批其他工具仍可能没有配对结果

因此，模型输出的并不是一项可以直接执行的命令，而是一份操作提案。运行时必须先把提案转化成确定的执行事实，再决定它是否安全、何时执行，以及将哪些结果分别交给模型和用户。

ZCode 中，这条完整路径从 executeToolCallsForModelStep()（core/src/runtime/methods/turn-tools.ts:43）开始，经过调度器与 ToolExecutor，最后重新回到对话历史：

    B --> C["参数处理<br/>解析、校验、规范化"]
    C --> D["调度<br/>并行组与执行顺序"]

为了避免被内部类型和函数名淹没，可以先把这条链分成三段：

阶段核心问题对应机制
执行前这是什么操作，何时执行，能否执行？准入、参数规范化、调度、权限
执行中如何限制它，并在需要时停止？环境端口、超时、取消
执行后哪些内容交给用户和模型，如何保证历史完整？结果投影、容量限制、配对持久化

后文虽然会进入具体源码，但始终围绕这三个问题展开。

调用准入：模型输出只是提案

名称与调用 ID：先建立身份

工具调用首先要有稳定的身份：toolCallId 标识这一次调用，name 决定去注册表中查找哪个 ToolEntry（工具的注册档案）。无论后面经历权限等待、并行执行还是失败恢复，系统都依靠这个 ID 把事件、界面状态和最终结果关联起来。

非流式响应在 model.ts:145 统一经过 normalizeModelToolCallsForRuntime()；流式响应则在收到完整 tool_call 事件时执行同样的规范化。流式路径还维护一个 toolCallIds 集合（model.ts:390）：如果适配器重复投递同一个 ID，运行时只接受第一次，避免同一次模型响应触发重复执行。

名称为空时有一个不直观的例外。对于已经带有调用 ID、并且需要由客户端执行的调用，运行时不会立刻终止整个 Turn，而是保留原始空名称，让执行器走“工具未注册”的失败路径。这样模型仍能收到与该 tool_use 配对的错误结果。

if (!entry) {
  return createErrorResult(
    toolCall,
    createCoreError(CoreErrorType.ToolNotFound, ...),
  );
}

这里反映了一条贯穿全文的规则：一旦模型已经声明了工具调用，错误也必须成为一个工具结果。 如果此处只抛出异常，模型下一次收到的历史将只有 tool_use、没有 tool_result，整个会话可能被提供商拒绝。

工具状态：先记录，再执行

调用身份确定后，运行时先为每个工具创建并持久化一个 pending part，即一条“等待执行的工具记录”（turn-tools.ts:99 起），随后才进行调度和执行。工具在界面和存储中的状态大致按以下顺序变化：

图表加载中…

stateDiagram-v2
    [*] --> Pending: tool_use 已闭合
    Pending --> Queued: 已进入调度计划
    Queued --> Running: 所属批次开始
    Running --> Completed: 成功结果
    Running --> Error: 失败或取消结果

为什么需要在真正执行前保存 pending 状态？因为执行可能在任意位置中断。如果只有函数返回后才记录，进程退出时系统甚至无法回答“模型是否曾经发起过这次调用”。先记录调用，再逐步更新状态，界面显示、冷恢复与流式恢复才共享同一份事实。

Q：工具不存在时，为什么不在注册表查询失败后直接终止 Turn？

A：因为“工具不存在”是模型可以理解并修正的业务失败，而不是运行时无法继续的内部故障。将它包装成结构化结果，既能关闭 tool_use/tool_result 配对，也能让模型在下一轮改用真实存在的工具。错误在这里不是历史之外的异常，而是历史中的一条合法记录。

至此，运行时只确认了“这是哪一次调用”，还没有确认“它究竟要做什么”。下一步是把模型给出的参数收敛为唯一的执行事实。

参数边界：从原始输入到执行事实

回到开头的 Edit：模型给出的路径和替换文本看似完整，但“可以解析”与“可以执行”之间还有很长的距离。ZCode 在执行函数（handler）之前依次设置了四道边界。

结构处理：兼容不稳定的适配器输出

第一步是 prepareInitialToolExecutionInput()（tool/input-normalization.ts）。某些模型适配器会把参数对象作为 JSON 字符串返回，因此运行时先尝试解析顶层字符串：

"{\"file_path\":\"server.ts\",\"old_string\":\"...\",\"new_string\":\"...\"}"
                                  ↓
{ file_path: "server.ts", old_string: "...", new_string: "..." }

解析失败不会让执行器本身崩溃，而是保留原值，随后由统一校验路径生成可恢复的参数错误。

如果工具提供了 runtimeInputSchema，运行时接着调用它的 safeParse。以 Zod 为例，这一步不仅检查类型，还可以完成默认值填充与预处理。之后，validateInitialModelToolInput() 再依据提供给模型的 JSON Schema 校验规范化结果。

这两套 schema 的职责并不重复：

schema面向谁主要职责
inputSchema模型与通用运行时描述公开参数契约，并生成模型可见的校验错误
runtimeInputSchema工具实现执行运行时转换、默认值与更严格的类型检查

首次参数校验失败时，错误内容会明确告诉模型哪些字段不符合要求，使模型能够在下一轮自行修正。

语义检查：结构正确仍不代表可执行

JSON Schema 只能判断“字段是否存在、类型是否正确”，无法回答更具体的问题。例如，一个任务 ID 的格式可能正确，但它对应的后台任务已经结束；一个工作流模型名称可能是字符串，却不在当前模型目录中。

因此，ToolEntry 还可以提供 validateInput。它位于 Hook 和权限判断之前（call-runner.ts:187）：无效调用无需触发扩展逻辑，更不应让用户批准一项注定失败的操作。

这种校验返回的是 ToolHandlerFailure，而不是任意异常：

interface ToolHandlerFailure {
  result: false;
  errorCode: number;
  message: string;
}

它代表可预期、可向模型说明的业务失败。执行器会把它转换为统一的工具错误事件和模型可见结果，而不另外建立一套失败生命周期。

输入解析：权限必须看到真正会执行的内容

通过结构与语义检查之后，工具还可以通过 resolveInput 把参数解析成规范形（call-runner.ts:207）。这一步刻意放在 PreToolUse 扩展钩子（Hook）和权限判断之前。

原因可以用相对路径说明。模型给出的可能是：

{ "file_path": "src/server.ts" }

真正的执行目标却取决于当前工作目录。若权限系统看到的是相对路径，而 handler 最终操作的是规范化后的绝对目标，用户批准的内容与实际执行的内容就不一致。ZCode 的顺序是：

模型原始输入
  → runtime schema 解析
  → JSON Schema 校验
  → 工具语义校验
  → resolveInput 得到执行事实
  → Hook 与权限判断
  → handler 使用同一份输入

这样，策略读取的参数、确认界面展示的参数与 handler 最终接收的参数才是同一份数据；不同版本的输入表达也会在执行前收敛到同一种形式。

Hook 改写：修改之后必须重新校验

PreToolUse Hook 可以拒绝调用、补充上下文，也可以修改输入。修改后的输入会再次经过规范化和 schema 校验（call-runner.ts:256）。这是必要的，因为扩展代码与模型一样，都不能绕过工具的输入边界。

权限阶段的 Hook 甚至可能修改目标路径。此时仅做 schema 校验仍然不够：输入变了，原先的权限判断也失效了。 recheckPermissionHookModifiedInput() 会针对新参数重新计算权限（permission-flow.ts:250），防止“批准 A，执行 B”。

Q：为什么 resolveInput 必须发生在权限确认之前，而不是让 handler 自己处理？

A：权限确认保护的不是模型写下的字符串，而是真实副作用。如果参数解析留在 handler 内部，策略与用户只能批准一个近似描述，执行时却可能得到不同的目标。先把输入解析成唯一的执行事实，再让所有策略读取同一份数据，权限才具有实际意义。

参数边界解决了“实际要做什么”。接下来，开头的 Edit 和 Bash 仍然面临另一个问题：两者能否同时开始？

工具调度：并行是一项证明责任

模型一次响应可以包含多个工具调用。运行时不能简单地全部串行——这会浪费互不影响的读取时间；也不能全部并行——例如开头的测试命令必须等文件修改完成，两个写操作也可能相互覆盖。

调度依据：从元数据推导，而不是猜测名称

scheduleTools()（runtime/methods/tools.ts:38）从注册表读取每个工具的元数据，转换成 ToolDependency：

{
  toolCallId,
  toolName,
  dependsOn: [],
  readOnly,
  destructive,
  concurrentSafe,
  sideEffectScope,
}

ToolScheduler.canRunInParallel()（tool/scheduler.ts:85）再按以下规则判断：

  • 破坏性工具不能并行；
  • concurrentSafe: true 明确允许并行；
  • concurrentSafe: false 明确禁止并行；
  • 只读工具可以并行；
  • 没有副作用（sideEffectScope === "none"）的工具可以并行。

对比三个内置工具即可看出差异：

工具readOnlyconcurrentSafe副作用范围调度结果
Globtruetruenone可与同组安全工具并行
Editfalsefalseworkspace单独执行
Bashfalsefalsesystem单独执行

即使某一条 Bash 命令只是 git status，调度器仍采用 Bash 的静态声明，保守地把它串行执行。输入相关的只读命令识别主要服务于权限判断，不会反过来扩大调度并发。这种不对称是有意的：权限误判通常多一次确认，而并发误判可能改变执行结果。

执行计划：拓扑排序与并行组

ToolScheduler 支持显式依赖、拓扑排序与环检测（tool/scheduler.ts:105），然后按依赖层级生成并行组（第 154 行）。不过，当前模型调用接入路径为每个调用传入的 dependsOn 都是空数组。也就是说，调度器具备依赖图能力，但本路径的实际排序主要由调用声明顺序和并发安全元数据决定。

假设模型按以下顺序返回：

Glob A, Glob B, Edit C, Bash D

得到的执行组近似为：

[Glob A, Glob B] → [Edit C] → [Bash D]

同一并行组内部通过 Promise.all 执行，但并发数默认不超过 10；组与组之间严格按顺序推进。

普通工具失败不会自动跳过所有后续组。batch-runner.ts:130 的注释记录了旧策略的问题：过去，一个非并发安全工具失败后会截断后续调用，结果是 TodoWrite 一类局部失败也可能阻止后面的子 Agent 工作。现在只有结果明确携带 stopTurnAfterResult 时，后续组才会被转换为取消结果。

结果归并：并发完成顺序不等于历史顺序

并行工具的完成顺序是不确定的。若直接按完成先后写回历史，同一份模型输出可能在不同机器上形成不同的消息顺序。

ZCode 在 turn-tools.ts:242 按模型最初声明的 coreToolCalls 顺序重新取回结果：

const results = coreToolCalls
  .map((toolCall) => resultById.get(toolCall.id))
  .filter((result) => result !== undefined);

因此，并发只影响等待时间，不改变对话历史的确定顺序。

Q：为什么不根据工具名维护一张“可以并行”的白名单？

A：工具名只是标识，不能完整表达行为。真正与并发相关的是它是否只读、是否具有副作用、作者是否明确保证并发安全。把这些事实声明在 ToolEntry 中，调度器才能对内置工具、MCP 工具和未来扩展使用同一套规则。

调度器回答的是“何时执行”，不是“是否允许执行”。即使 Edit 已经被安排在 Bash 之前，它仍要经过权限系统的判断。

权限协议：从策略判断到用户决定

工具通过参数校验并进入执行组之后，仍不代表可以执行。resolveToolPermission()（tool/executor/permission-flow.ts:41）需要回答两个不同的问题：

  1. 当前规则判断是什么：允许、询问还是拒绝？
  2. 如果需要询问，谁来作出最终决定？

将两者分开，是理解 ZCode 权限系统的关键。

策略判断：allow / ask / deny 三态

PermissionService.checkPermission()（permission/service.ts:97）综合以下信息：

  • 工具声明的风险等级、副作用范围和交互要求；
  • 当前协作模式，例如 plan、edit、build；
  • 项目级 allow、ask、deny 规则；
  • 针对 alwaysAsk 工具在本会话临时授予的规则；
  • 针对 WebFetch、工作流草稿等能力的专门规则；
  • PreToolUse Hook 给出的权限倾向。

返回结果不是简单的布尔值，而是包含来源的结构化决定：

决定含义后续行为
allow已有规则明确允许直接进入执行阶段
deny硬性规则拒绝生成权限错误结果
ask需要外部决定发出权限请求并等待应答

规则有明确优先级。例如，项目 deny/ask 位于普通项目 allow 之前；plan 模式会在写操作放行之前介入；工具声明的 alwaysAsk 也不能被常规放行路径轻易覆盖。权限结果携带 ruleId、riskLevel 与 sideEffectScope，日志和界面因而可以解释“为什么询问”或“为什么拒绝”。

确认等待：Hook 与界面并发竞赛

当决定为 ask 时，运行时先发出 PermissionRequested 事件，使界面能够展示工具名、参数、风险等级和建议的规则更新。随后有两个潜在的应答方：

  • Permission Broker（权限交互通道）：承接桌面界面或终端中的用户选择；
  • PermissionRequest Hook（权限请求钩子）：允许外部审批系统或扩展程序作出决定。

二者不是串行执行，而是通过 racePermissionResponders()（permission-responder-race.ts:38）并发竞赛：谁先给出有效结果，谁就生效，另一方立即收到取消信号。

源码注释记录了这套竞赛的由来：旧路径先等待 Hook 链结束，再向 Broker 注册应答。如果同步 Hook 本身正在等待外部审批，确认界面虽然已经出现，用户点击却没有已注册的接收方，Turn 会永久等待。现在 Broker 在竞赛内部优先同步建立应答通道，Hook 与它并发运行。

竞赛的收尾顺序同样经过设计：先兑现胜者结果，再取消败者（permission-responder-race.ts:54）。否则，如果败者的清理过程阻塞，胜者已经作出的决定也无法继续向下推进。

Hook 自身发生故障时不会替用户作出拒绝决定，而是退出竞赛，让 Broker 继续等待。这体现了权限系统中的“故障时保持原有决策者”：辅助审批渠道失效，不应擅自代替用户选择。

参数修改：再次确认执行边界

权限应答除了 allow 和 deny，还可以返回 modify。例如，用户可以将一条命令修改为更安全的形式后允许执行。

修改后的参数必须重新规范化并校验。如果修改来自 PermissionRequest Hook，系统还会重新运行权限判断，因为新的路径或命令可能匹配不同规则。只有新输入也通过校验和策略检查，才会成为 handler 最终接收的 executionInput。

权限选择还可能产生两种不同生命周期的规则：

规则保存位置生命周期
本会话不再重复询问 alwaysAsk 工具PermissionService 内存规则集随当前会话实例结束
项目级规则更新session store 中的项目权限后续会话继续有效

两者不能混为一谈。一次临时授权不应悄然变成项目的长期政策；长期规则也必须在确认后可靠保存，否则界面显示“以后允许”而实际没有生效。

Q：为什么权限确认不能只返回一个 true/false？

A：权限不仅要决定能否执行，还要解释规则来源、支持修改参数、记录用户选择的适用范围，并允许多个应答渠道协作。布尔值只能表达结果，无法承载这段协议。结构化决定使 UI、Hook、持久化与执行器共享同一种语义。

经过这一步，开头的 Edit 才从“模型建议修改文件”变成“运行时允许修改这个确定文件”。下面才进入真正产生副作用的阶段。

受控执行：超时、取消与环境端口

只有在权限允许之后，执行器才发出 ToolCallStarted 事件（call-runner.ts:329）。这条边界很重要：pending 和 permission 表示“准备执行”，started 才表示工具即将产生真实行为。

取消信号：沿调用链传递

执行器为当前调用创建独立的 AbortController，再通过 linkAbortSignal() 将 Turn 的取消信号连接进来：

flowchart LR
    A["用户停止 Turn"] --> B["Turn AbortSignal"]
    B --> C["工具调用 AbortController"]
    C --> D["ToolExecutionContext.abortSignal"]
    D --> E["文件 / 命令 / 网络适配器"]

handler 不是被运行时从外部强制终止，而是在文件、命令或网络操作的可取消边界处收到信号并退出。以 Glob 为例，fileSystemPort.searchFiles() 会同时接收这个取消信号。

这也是为什么取消能力必须成为全链路约定：只要某一层没有继续传递信号，该层下面的操作就无法及时响应用户停止。

超时预算：只计算真正属于工具的等待

普通 Promise.race([handler, timeout]) 使用固定墙钟时间，但 ZCode 的 ToolDeadline（工具截止计时器，tool/executor/timeout.ts:19）可以暂停。

考虑 WebSearch 工具：handler 内部可能再次请求模型，而模型请求需要先等待进程级的网络准入。如果系统限流使它在内部队列等待 30 秒，这 30 秒不应被算作提供商执行超时，否则并发越受限，工具越容易被错误取消。

observeToolAdmissionClock() 监听当前工具的模型网络状态：

model_request_queued   → 暂停 deadline
model_request_admitted → 恢复 deadline

因此，超时约束的是工具自身的执行预算，而不是系统内部的排队时间。退避等待仍会计时，因为那反映的是提供商当前不可用；只有运行时自己的准入等待会被扣除。

不同工具还可以声明不同的超时政策：默认时长、最大时长、是否允许调用方覆盖，以及取消后的清理宽限期。Bash 允许在政策上限内请求更长时间，Edit 则固定为 30 秒。

环境访问：handler 只拿到受控端口

权限通过之后，call-runner.ts 才构造 ToolExecutionContext，其中包含：

  • fileSystemPort、executionPort、httpClientPort 等环境端口；
  • 工作目录、工作区根目录与 workspaceIdentity；
  • 当前 session、Turn 与 trace 标识；
  • 取消信号与事件出口；
  • 仅在相应运行环境存在时才注入的子 Agent、浏览器、工作流等能力。

handler 不需要知道当前运行在桌面、本地测试还是远程工作区。它只依赖端口，并且只能使用装配层实际提供的能力。端口缺失时，工具返回配置错误，而不是自行寻找另一条未经控制的访问路径。

失败收口：把异常转换为结果

handler 执行、输出序列化或 PostToolUse Hook 都可能失败。call-runner.ts:561 的统一失败路径会：

  1. 运行 PostToolUseFailure Hook；
  2. 将异常投影为结构化 ToolExecutionResult；
  3. 发出 ToolCallError 事件；
  4. 按失败阶段记录遥测；
  5. 返回失败结果，而不是让这一次工具调用消失。

执行器同时区分两个时间指标：durationMs 主要表示 handler 的执行时间，totalMs 则包含注册表查询、校验、Hook、权限等待、执行、序列化和后置 Hook。前者用于分析工具本身，后者更接近用户感知的等待。

Q：为什么工具超时后还要向 handler 传递取消信号？Promise 已经可以先返回超时错误。

A：先返回只能结束等待，不能停止真实副作用。子进程、文件操作或网络请求仍可能在后台继续。超时路径先中止当前调用的 AbortController，再返回结构化错误，使底层适配器有机会终止工作并执行清理。

此时工具已经得到成功或失败的原始结果，但原始结果还不适合直接交给用户和模型。执行链由此进入最后一段：结果如何表达。

结果边界：同一次输出的四种视图

handler 返回以后，结果还不能直接进入对话历史。它首先通过 runtimeOutputSchema 或 outputSchema 校验（call-runner.ts:456），防止工具实现违反自己声明的返回契约。

校验通过后，同一份结果会形成至少四种用途不同的视图。这里的“投影”并不是复制四份业务状态，而是从同一执行事实生成四种表达：

视图面向对象关注点
output运行时内部保留结构化原始结果，供工作区检查点、后台任务等机制使用
display用户界面工具标题、摘要、差异或 MCP 展示信息
modelContent下一轮模型请求紧凑、可行动，并受上下文预算约束
serialization事件与观测截断状态、原始字节数、返回字节数、artifact 路径

这解释了为什么 ToolExecutionResult 不能只有一个字符串。用户、模型、恢复机制和观测系统消费的是同一次执行事实，但所需表达不同。

模型内容：不是原始输出的机械复制

工具可以通过 formatModelContent 将结构化输出转成适合模型继续推理的内容。例如 Edit 成功后，模型需要知道文件已更新、当前文件状态是否仍可继续编辑，而不需要再次接收完整文件。

如果格式化结果为空，serializeOutput()（tool/executor/result-serialization.ts:46）会生成明确占位：

(Bash completed with no output)

空字符串不能直接表示成功，因为模型可能把它误解为工具结果缺失。

结果预算：截断或转存 artifact

每个工具可以声明 resultBudget。以三个工具为例：

工具模型预算策略预览方向
Glob100 KB超出后转存 artifact头部
Edit100 KB截断头部
Bash30 KB超出后转存 artifact尾部

Bash 保留尾部是因为命令报错、测试总结和退出原因通常出现在末尾；Glob 保留头部则便于先看到最靠前的一批匹配结果。预算不是统一截取前 N 个字符，而是工具契约的一部分。

当结果超出预算且策略为 artifact（独立保存的完整结果）时，完整内容由 artifactStore 保存，模型收到预览、原始大小与引用位置。如果 artifact 写入失败，系统不会把一次成功的工具执行改判为失败，而是回到统一截断路径（result-serialization.ts:294）：结果仍然可见，同时避免大体积内容直接进入上下文。

PostToolUse Hook 补充的诊断上下文也必须服从同一预算。它不能因为发生在序列化之后，就绕过前面建立的大小限制。

展示与推理：分别构造

createToolResultDisplay() 根据工具类型构造界面展示；serializeOutput() 构造模型内容。两条路径读取同一原始输出，却互不冒充：

  • UI 可以展示结构化差异、运行状态或媒体信息；
  • 模型只接收继续任务所需的紧凑内容；
  • 观测事件记录是否截断和字节统计；
  • artifact 保存超出上下文预算但可能需要回查的原文。

Q：为什么不把 UI 中显示的结果原样发给模型？

A：界面展示追求可读性和交互性，模型输入追求信息密度与协议稳定性。一个差异视图可能适合人类展开查看，却不适合作为数万 token 的下一轮输入。分别投影可以让两者共享执行事实，又不共享不合适的表示形式。

结果的多种表达已经准备完成，最后还差一步：把它们按正确顺序提交，使本轮对话重新成为一段完整历史。

历史闭合：所有路径都必须产生结果

工具执行完成后，运行时按模型声明顺序遍历结果，并为每个调用完成以下工作（turn-tools.ts:280 起）：

  1. 记录工具用量；
  2. 将持久化 part 更新为 completed 或 error；
  3. 把 modelContent 作为 tool_result 提交到下一轮请求历史；
  4. 对文件修改生成工作区检查点（workspace checkpoint）；
  5. 发出流式恢复锚点与工具账本事件；
  6. 处理工具结果附带的后续用户输入。

其中最重要的顺序是：先关闭工具结果，再处理附加工作。 checkpoint 创建失败不应让已经成功的工具重新变成没有结果的调用。

取消发生在工具批次中间

假设模型一次调用三个工具，用户在第二个工具执行期间停止 Turn。此时 assistant 的三个 tool_use 已经进入历史，运行时不能立即抛出取消错误。

turn-tools.ts:142 的注释明确要求：继续把取消信号交给执行器，由每个尚未完成的调用产生 ToolCancelled 结果；全部配对结果提交之后，Turn 循环才能感知取消并退出。

tool_use A ── tool_result A（成功）
tool_use B ── tool_result B（已取消）
tool_use C ── tool_result C（已取消）

甚至取消发生在 checkpoint 阶段时，运行时也会先记住这次取消，继续提交同批其他工具的结果，最后再抛出取消（turn-tools.ts:280-421）。这是为了避免一个附加操作阻止其余工具完成协议闭合。

普通失败不终止整个批次

一个工具参数错误或执行失败，并不等于后续工具都必须取消。普通失败会作为结果返回模型，调度器继续后续组。只有工具结果明确请求 stopTurnAfterResult——例如某些终态提交工具——后续调用才统一生成取消结果。

因此，执行失败与控制流终止是两个独立维度：

工具结果当前结果后续组
成功正常提交继续
普通失败错误结果提交继续
请求终止 Turn当前结果提交后续调用生成取消结果
用户取消所有未完成调用生成取消结果配对完成后退出

这避免了用“异常是否抛出”来间接控制整个 Turn。

Q：为什么 checkpoint 要放在 tool_result 提交之后？

A：checkpoint 是工具成功后的增强能力，而 tool_result 是模型协议要求的不变式。增强能力失败可以降级，协议闭合不能被阻断。先完成必要事实，再执行附加记录，故障边界才清晰。

至此，常规工具调用已经走完了从提案到历史记录的全过程。最后再看一个更苛刻的场景：工具在模型响应尚未结束时就提前执行。

流式执行：模型还未结束，工具已经开始

到目前为止，我们默认模型完整返回所有工具调用后才开始执行。ZCode 还有一项更进一步的优化：满足严格条件的只读工具，可以在模型响应流仍未结束时提前执行。

入口是 createStreamingToolCoordinator()（runtime/methods/streaming-tool-coordinator.ts）。当流中出现一个完整的 tool_call 事件时，shouldExecuteToolDuringStream()（第 339 行）检查：

  • 工具不是由提供商代为执行；
  • 开启了模型流式输出与流式工具执行；
  • readOnly 为 true；
  • concurrentSafe 为 true；
  • destructive 为 false；
  • 不需要批准或用户交互；
  • sideEffectScope 为 none。

只有全部满足，工具才会在流结束前进入调度。Glob 符合这一条件，Edit 与 Bash 不符合。

这样做可以把“模型继续生成后续内容”的时间与“只读工具执行”的时间重叠，但它同时引入了新的恢复问题：如果工具已经执行完成，模型流随后中断，该怎么办？

ZCode 的恢复步骤是：

  1. 收集已经完成的流式工具结果；
  2. 对执行状态不明确或尚未执行的调用生成合成错误结果；
  3. 将 assistant tool-call 与所有结果一起提交到请求历史；
  4. 以最近一个已提交工具结果为恢复锚点，重新发起模型请求。

也就是说，性能优化不能改变历史不变式。即使模型流在最不利的位置断开，运行时仍要构造一段自洽历史，再尝试恢复。

Q：为什么流式提前执行只允许无副作用工具？

A：流尚未结束时，模型的最终响应还没有稳定下来，连接也可能失败并重试。只读、并发安全且无需授权的工具即使提前执行，最多造成重复计算；写文件或运行命令若在恢复中重复，可能产生不可逆的环境变化。性能优化的适用范围必须由可重复执行性约束。

总结：工具执行器是一条可信边界

回看开头的一行 run_tools，ZCode 实际建立了六层保护：

  1. 模型输出是提案，不是执行事实：名称、ID、参数与工具存在性都需要准入。
  2. 先规范化，再应用策略：Hook、权限界面与 handler 必须看到同一份执行参数。
  3. 并行需要显式证明安全：调度依据是副作用与并发元数据，完成后仍按声明顺序归并。
  4. 权限是一套多参与方协议：规则、用户界面和 Hook 共同形成 allow、ask、deny、modify 的决策过程。
  5. 结果需要按消费者分别投影：运行时、UI、模型与观测系统不应共享一个未经约束的字符串。
  6. 每条路径都要关闭历史：未知工具、拒绝、超时、取消和断流最终都必须形成配对结果。

因此，工具执行器的核心职责不是“找到函数并调用”，而是建立一条可信边界：左侧是不稳定、不可直接信任的模型输出，右侧是真实文件、进程与网络；中间每一层都在缩小不确定性，直到一次操作可以被安全执行并准确记录。
